# CertSentry 证书哨兵 —— 技术调研报告

> 版本：v1.1（由 Django 方案改为 FastAPI 方案）　日期：2026-11-09
> 配套文档：[01-需求开发报告.md](01-需求开发报告.md)
> 标记说明：✅ 已从官方来源核实；⚠️ 基于已有知识，开工前建议再确认一次。

---

## 1. 调研结论（TLDR）

- 后端：**FastAPI 0.162 + SQLAlchemy 2.1（asyncio）+ asyncpg + Alembic + Pydantic v2**，Python 3.13。
- 检测引擎：**独立的 asyncio worker 进程**，不用 Celery。worker 用 PostgreSQL `SELECT ... FOR UPDATE SKIP LOCKED` 领取到期目标，可以起多个实例水平扩展。
- 通知：**事务性 outbox 表**，告警记录和待发通知在同一个事务写入，单独的发送循环负责投递和重试。
- 前端：**Vue 3 + TypeScript + Vite**，从 OpenAPI 自动生成类型安全的 API 客户端。
- 证书解析用 **cryptography 50**；资产发现优先用 **SSLMate Cert Spotter API**。
- 整套用 docker-compose 部署：Caddy、api、worker、PostgreSQL、Redis。

### 2.2 为什么这个项目改用 FastAPI

上一版选 Django，是因为认证、权限、后台这些功能 Django 开箱即用。现在 Django 名额给了业务更重的发票报销系统，证书监控改成 FastAPI，理由如下：

- **核心负载是并发 IO。** 1000 个目标就是几千次 DNS 查询加 TLS 握手，每次大部分时间在等网络。asyncio 单进程就能同时维持几百个连接，不需要 Celery 的 worker 池。
- **API 优先。** 这个产品的价值很大一部分在开放 API、状态徽章和 Webhook，FastAPI 自动生成的 OpenAPI 文档可以直接给用户调试。
- **两个项目技术栈不重叠。** Django 项目体现 ORM、Admin、模板、Celery；FastAPI 项目体现 asyncio、SQLAlchemy 2.x、依赖注入、自己实现认证和权限。面试时两个项目能讲的内容不重复。
- **代价要承认。** 登录、权限、管理后台、迁移都要自己搭，这部分工作量比 Django 多一到两周。但这也是面试官会问的地方："Django 帮你做好的事，你在 FastAPI 里是怎么做的？"

### 2.3 为什么不用 Celery

| 方案 | 取舍 |
|---|---|
| **asyncio worker + PostgreSQL SKIP LOCKED（选定）** | 少一个中间件；任务状态就在业务表里，`next_check_at` 本身就是队列；多 worker 并发领取不重复；面试能讲清楚原理 |
| Celery | 本身是同步模型，跑 async 代码要额外处理事件循环；对"按时间扫描到期目标"这种需求，它的 beat 调度反而绕了一圈 |
| Taskiq 0.13（异步任务队列）✅ | 原生 async，有 Redis broker，但对本项目来说依然是多一层；如果后期要做通用后台任务（导出、批量导入）再引入 |
| APScheduler | 单进程调度，多实例部署会重复执行 |

领取任务的核心 SQL：

```sql
WITH due AS (
    SELECT id FROM target
    WHERE NOT is_paused AND next_check_at <= now()
    ORDER BY next_check_at
    LIMIT 100
    FOR UPDATE SKIP LOCKED
)
UPDATE target t
SET next_check_at = now() + t.interval,
    locked_until  = now() + interval '2 minutes'
FROM due WHERE t.id = due.id
RETURNING t.id, t.hostname, t.port, t.sni;
```

- 多个 worker 同时执行这条语句，`SKIP LOCKED` 让它们各自拿到不同的行。
- 先推进 `next_check_at` 再检测：worker 崩溃时，这个目标会在下一个周期重新检测，不会卡死。
- `locked_until` 防止手动触发的检测和定时检测撞车。

### 2.4 前端方案

**Vue 3 + TypeScript + Vite + Element Plus（或 Naive UI）**。

- FastAPI 输出 OpenAPI，前端用 `openapi-typescript` 生成类型，接口字段改了前端编译就报错。

## 3. FastAPI 里要自己实现的部分

### 3.1 认证

| 项目 | 方案 |
|---|---|
| 密码哈希 | `argon2-cffi`（或 `pwdlib`），不要用已经停止维护的 passlib ⚠️ |
| 会话 | 短期 access token（JWT，15 分钟）+ 长期 refresh token（随机串，库内存哈希，可吊销，放在 `HttpOnly` Cookie） |
| 刷新令牌轮换 | 每次刷新签发新的 refresh token，旧的作废；检测到旧令牌被重用，就吊销该用户全部会话 |
| 邮箱验证、找回密码 | 一次性令牌，存哈希，30 分钟过期 |
| 登录限流 | Redis 计数：同一账号 5 次失败锁 15 分钟，同一 IP 每分钟 20 次 |
| API Token | `cs_` 前缀 + 32 字节随机串，只存 SHA-256；请求头 `Authorization: Bearer cs_xxx` |

### 3.2 多租户与权限（依赖注入）

```python
async def current_membership(
    org_slug: str,
    user: User = Depends(current_user),
    db: AsyncSession = Depends(get_db),
) -> Membership:
    m = await db.scalar(
        select(Membership).join(Organization)
        .where(Organization.slug == org_slug, Membership.user_id == user.id)
    )
    if m is None:
        raise HTTPException(404)   # 用 404 而不是 403，不泄露组织是否存在
    return m

def require_role(*roles: Role):
    async def checker(m: Membership = Depends(current_membership)) -> Membership:
        if m.role not in roles:
            raise HTTPException(403)
        return m
    return checker

@router.delete("/orgs/{org_slug}/targets/{target_id}")
async def delete_target(target_id: int, m = Depends(require_role(Role.OWNER, Role.ADMIN)), ...):
    ...
```

- 所有业务查询都通过一个 `TenantRepository` 进行，构造时传入 `org_id`，内部统一加 `where(Model.org_id == org_id)`。
- **租户隔离测试**：参数化遍历所有带 `{org_slug}` 的路由，用 B 组织成员的身份请求 A 组织资源，断言全部 404。新加路由会被测试自动覆盖。

## 4. 检测引擎设计

### 4.1 asyncio 握手

```python
import asyncio, ssl
from cryptography import x509

async def fetch_cert(hostname: str, ip: str, port: int, timeout: float = 10.0):
    ctx = ssl.create_default_context()
    reader, writer = await asyncio.wait_for(
        asyncio.open_connection(ip, port, ssl=ctx, server_hostname=hostname),
        timeout,
    )
    try:
        sslobj = writer.get_extra_info("ssl_object")
        leaf = x509.load_der_x509_certificate(sslobj.getpeercert(binary_form=True))
        chain = sslobj.get_verified_chain()   # Python 3.13 新增 ✅⚠️ 开工第一天写脚本确认
        return leaf, chain, sslobj.version()
    finally:
        writer.close()
        await writer.wait_closed()
```

要点：

- **先解析再连接**：`dns.asyncresolver` 解析 A/AAAA，校验 IP 不在保留地址段后，把 IP 直接传给 `open_connection`，SNI 用域名。这样既防 SSRF 和 DNS rebinding，又能逐个节点检测。
- **并发控制**：全局 `asyncio.Semaphore(200)` 限制同时连接数；对同一个 IP 再加一个小信号量，避免同时打满一台服务器。
- **验证失败时的诊断**：默认上下文验证失败会抛 `ssl.SSLCertVerificationError`，它的 `verify_code` 能区分过期、自签名、域名不匹配。再用 `CERT_NONE` 上下文连一次拿到证书内容，用于展示，结果标记为"不可信"。
- 主机名匹配交给 `ssl` 默认上下文，不自己写通配符匹配。

### 4.2 解析字段

| 字段 | cryptography API |
|---|---|
| SAN | `cert.extensions.get_extension_for_class(x509.SubjectAlternativeName)` |
| 有效期 | `cert.not_valid_before_utc` / `not_valid_after_utc` |
| 指纹 | `cert.fingerprint(hashes.SHA256())` |
| 公钥 | `cert.public_key()`，判断 RSA 长度或 EC 曲线 |
| 签名算法 | `cert.signature_hash_algorithm` |
| 颁发者 | `cert.issuer.rfc4514_string()` |

### 4.3 告警与通知：事务性 outbox

```python
async with db.begin():
    # 1. 写检测结果
    db.add(CheckResult(...))
    # 2. 去重插入告警；冲突说明这个阈值已经告警过
    event_id = await db.scalar(
        insert(AlertEvent).values(target_id=t.id, kind="expiry",
                                  threshold=14, cert_sha256=fp)
        .on_conflict_do_nothing(index_elements=["target_id", "kind", "threshold", "cert_sha256"])
        .returning(AlertEvent.id)
    )
    # 3. 同一事务写入待发通知
    if event_id:
        for ch in channels:
            db.add(NotificationOutbox(alert_event_id=event_id, channel_id=ch.id, payload=...))
```

- 发送循环同样用 `SKIP LOCKED` 领取 `status='pending' AND next_retry_at <= now()` 的行，调用 Webhook，成功标 `sent`，失败按 1、5、30 分钟、2 小时、12 小时退避，5 次后标 `dead` 并在控制台显示。
- 好处：进程崩溃不会丢通知，也不会因为重试重复告警。这是面试里很好讲的一个点。

## 5. 资产发现（CT 日志）

| 数据源 | 认证 | 限制 | 结论 |
|---|---|---|---|
| **SSLMate Cert Spotter API v1** | 少量查询可匿名；生产用免费 API Key ✅ | 免费额度未公开，可能随时调整 ✅ | **主用** |
| crt.sh | 无需认证 ⚠️ | 公共实例经常超时，无 SLA | 备用 |
| 自建 CT 日志消费 | — | 存储和运维成本过高 | 不做 |

```
GET https://api.certspotter.com/v1/issuances?domain=example.com&include_subdomains=true&expand=dns_names&expand=issuer
Authorization: Bearer <key>
```

用 `after=<last_id>` 增量翻页，每个根域名记录上次拉到的 id，每天只拉增量。

**归属验证**：要求用户添加 `_certsentry-verify.<域名>` 的 TXT 记录，验证通过后才开启发现。

**已知限制**：私有 CA 和自签名证书发现不了；通配符证书不暴露具体子域名；CT 入库有延迟。

## 6. 通知渠道

| 渠道 | 接入方式 | 注意点 |
|---|---|---|
| 邮件 | `aiosmtplib` 异步发送；SaaS 用第三方事务邮件服务 ⚠️ | 配置 SPF、DKIM、DMARC |
| 企业微信群机器人 | POST JSON，`msgtype=markdown` ⚠️ | 每个机器人每分钟 20 条，需合并消息 |
| 钉钉群机器人 | 加签：`timestamp + "\n" + secret` 做 HMAC-SHA256 后 Base64 ⚠️ | 以官方文档为准 |
| 飞书群机器人 | 带 `timestamp` 和 `sign` ⚠️ | 服务器时间要准 |
| 通用 Webhook | POST JSON，带 `X-Certsentry-Signature`（HMAC-SHA256） | 文档给出验签示例 |

每个渠道实现同一个 `Notifier` 协议（`async def send(msg: AlertMessage) -> None`），新增渠道不改发送循环。

## 7. 数据模型补充

- `Target`：唯一约束 `(org_id, hostname, port)`；部分索引 `(next_check_at) WHERE NOT is_paused`，供领取任务使用。
- `Certificate`：`sha256` 全局唯一，跨租户共享；只能经由 `CheckResult` 关联查询。
- `CheckResult`：按月分区，保留 90 天；索引 `(target_id, checked_at DESC)`。
- `AlertEvent`：唯一约束 `(target_id, kind, threshold, cert_sha256)`。
- `NotificationOutbox`：部分索引 `(next_retry_at) WHERE status = 'pending'`。
- `Channel.config`：Fernet 加密，密钥来自环境变量。
- 迁移全部由 Alembic 管理，CI 中执行 `alembic upgrade head` 再 `alembic downgrade -1` 验证可回滚。

## 8. 安全设计

| 威胁 | 对策 |
|---|---|
| SSRF | 解析后校验 IP，拒绝回环、私网、链路本地（含 169.254.169.254 云元数据）、组播、保留段及 IPv6 等价段 |
| DNS rebinding | 校验和连接使用同一次解析结果，IP 直接传给连接函数 |
| 凭证泄露 | Webhook 密钥加密存储，只回显掩码；API Token 和 refresh token 只存哈希 |
| 越权 | 依赖注入统一校验成员与角色；租户隔离参数化测试 |
| 滥用 | 邮箱验证、组织额度、检测冷却、Redis 限流 |
| CSRF | refresh token Cookie 设 `SameSite=Strict`，并只在 `/auth/refresh` 路径下发送；其他接口用 `Authorization` 头，不依赖 Cookie |
| 传输 | Caddy 自动 HTTPS；HSTS |
| 依赖漏洞 | `pip-audit` 和 `npm audit` 接入 CI |

## 9. 部署架构

```
               ┌── Caddy（自动 HTTPS，托管 Vue 静态文件，反代 /api）
  浏览器 ──────┤
               └── api（uvicorn，2 进程）──┬── PostgreSQL 17（业务数据 + 任务领取）
                                          └── Redis 7（限流、缓存）
               检测 worker × N ───────────┘（asyncio，不对外暴露）
               通知 sender × 1 ───────────┘
```

- 一台 2 核 2 GB 的香港或新加坡 VPS 可以支撑演示站，无需 ICP 备案。⚠️ 价格以实际为准。
- worker 和 sender 是同一个镜像的不同启动命令，`docker compose up --scale worker=3` 即可扩容。
- 每日 `pg_dump` 备份，保留 7 天。错误上报 Sentry，指标用 `prometheus-fastapi-instrumentator` 暴露。

## 11. 被否决的方案

| 方案 | 否决原因 |
|---|---|
| Django | 名额给了发票报销系统；本项目 IO 并发更适合 asyncio |
| Celery + Redis | 见 2.3 |
| SQLModel | 封装在 SQLAlchemy 之上，遇到复杂查询（CTE、ON CONFLICT、分区）仍要写原生 SQLAlchemy，不如直接用 |
| Tortoise ORM | 生态和文档不如 SQLAlchemy，面试认可度低 |
| `ssl.get_server_certificate` | 拿不到证书链 |
| 自建 CT 日志消费端 | 成本过高 |
| Kubernetes | 单机 compose 足够，没有真实规模不写 |
