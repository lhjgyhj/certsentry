## 1. 调研结论（TLDR）

- 技术栈：**Django 5.2 LTS + Django REST Framework 3.18 + Celery 5.7 + Redis + PostgreSQL 17 + HTMX + Tailwind CSS**，Python 3.13。
- 证书解析用 **cryptography 50**，不要用标准库 `ssl` 解析证书内容（标准库不解析 SAN 扩展）。
- 资产发现优先用 **SSLMate Cert Spotter API**，crt.sh 只做备用。
- 检测引擎与 Web 进程分离，检测 worker 放在独立网络，配合 DNS 解析后的 IP 校验防止 SSRF。
- 全部组件都有官方 Docker 镜像，`docker-compose up` 即可启动，符合"真实上线"目标。

### 2.2 为什么是 Django 而不是 FastAPI

- 需求里一半是 CRUD、权限、后台、表单，Django 的 ORM、Admin、认证、迁移、CSRF 防护开箱即用。FastAPI 要把这些自己拼起来。
- Django Admin 直接就是运营后台，MVP 阶段省下一整套管理界面。
- 面试叙事清晰：能讲多租户隔离、迁移、事务、Celery 集成，而不是"我用框架搭了几个接口"。
- FastAPI 留给下一个项目（依赖漏洞监控），两个项目技术栈不重复，简历更好看。

### 2.3 前端方案

**HTMX + Tailwind CSS + Alpine.js（少量）**，服务端渲染 Django 模板。

| 方案 | 取舍 |
|---|---|
| HTMX（选定） | 一个监控后台的交互（表格筛选、弹窗、轮询状态）HTMX 足够；不需要维护前后端两个工程；面试能讲"按交互复杂度选技术，而不是默认上 SPA" |
| Vue / React SPA | 交互复杂度不匹配，开发量翻倍，且你已有的 JS/TS 项目可以在别的项目里体现 |

### 2.4 任务队列

**Celery 5.7 + Redis + django-celery-beat**。

- 检测任务是典型的"定时 + 高并发 IO"，Celery 的 worker 池、重试、限流都现成。
- 用数据库调度（django-celery-beat）而不是静态 `beat_schedule`，因为每个目标的检测频率和 `next_check_at` 都不同，需要动态调度。
- 调度策略：beat 每分钟运行一次"派发器"任务，查询 `next_check_at <= now()` 的目标，批量投递检测任务，并立即把 `next_check_at` 推到下一周期（用 `UPDATE ... WHERE next_check_at <= now()` 保证幂等，多实例不会重复派发）。

## 3. 检测引擎设计

### 3.1 为什么不用标准库

`ssl.get_server_certificate()` 只返回叶子证书，不返回中间证书，无法判断证书链是否完整。`ssl.SSLSocket.getpeercert()` 返回的字典在较新 Python 里也不方便做算法判断。

选定方案：用标准库 `ssl` 建立连接（它负责 TLS 握手和系统信任库验证），用 `cryptography` 解析证书内容。

```python
import socket, ssl
from cryptography import x509
from cryptography.hazmat.primitives.serialization import Encoding

def fetch(hostname: str, ip: str, port: int, timeout: float = 10.0):
    ctx = ssl.create_default_context()
    # 连指定 IP，但用域名做 SNI 和主机名校验，才能发现"某个节点证书不同"
    with socket.create_connection((ip, port), timeout=timeout) as sock:
        with ctx.wrap_socket(sock, server_hostname=hostname) as ssock:
            der_chain = ssock.getpeercertchain()  # 3.13 提供完整链；低版本用 ssl.SSLObject
            leaf = x509.load_der_x509_certificate(ssock.getpeercert(binary_form=True))
            version = ssock.version()
    return leaf, der_chain, version
```

要点：

- **先 DNS 解析，再逐个 IP 连接**。解析与连接分开，才能做 SSRF 校验，也才能发现多节点证书不一致。
- DNS 用 `dnspython`，设置 3 秒超时，禁用搜索域（`search`），避免把 `intranet` 这类名字解析到内网。
- 主机名校验交给 `ssl` 的默认上下文，它按 RFC 6125 匹配 SAN 和通配符，不要自己写匹配逻辑。
- 证书链验证失败时，用一个 `verify_mode=CERT_NONE` 的上下文再连一次，只为了拿到证书内容做诊断（已过期、域名不匹配、自签名分别归类），这一次的结果标记为"不可信"。
- 超时：连接 10 秒，整个任务 20 秒硬超时，由 Celery `soft_time_limit` 保证。

### 3.2 解析字段

| 字段 | cryptography API |
|---|---|
| SAN | `cert.extensions.get_extension_for_class(x509.SubjectAlternativeName)` |
| 有效期 | `cert.not_valid_before_utc` / `not_valid_after_utc`（不要用已废弃的不带 `_utc` 的属性） |
| 指纹 | `cert.fingerprint(hashes.SHA256())` |
| 公钥 | `cert.public_key()`，判断 `RSAPublicKey.key_size` 或 `EllipticCurvePublicKey` |
| 签名算法 | `cert.signature_hash_algorithm` |
| 颁发者 | `cert.issuer.rfc4514_string()` |

### 3.3 并发模型

- Celery worker 使用 **gevent 池**（`-P gevent -c 200`）。检测是纯 IO，gevent 比 prefork 省内存一个数量级。
- 单个任务检测一个目标（含其全部 IP），不要把 1000 个目标塞进一个任务。
- 任务幂等：重复执行只是多写一条检测记录，告警去重由表保证（见 3.4）。
- DNS 和目标站点都可能限流，对同一域名的手动检测做 10 分钟冷却。

### 3.4 告警去重的实现

```sql
-- 同一证书周期、同一阈值只插入一次；并发 worker 也不会重复告警
INSERT INTO alert_event (target_id, kind, threshold, cert_sha256, sent_at)
VALUES (%s, 'expiry', 14, %s, now())
ON CONFLICT (target_id, kind, threshold, cert_sha256) DO NOTHING
RETURNING id;
```

返回了 id 才真正发送通知。发送失败则把记录标为 `failed` 并重试，而不是删除，避免重试风暴。

## 4. 资产发现（CT 日志）

### 4.1 数据源对比

| 数据源 | 认证 | 限制 | 结论 |
|---|---|---|---|
| **SSLMate Cert Spotter API v1** | 少量查询可匿名；生产用免费 API Key（Bearer）✅ | 免费额度未公开，且声明可能随时调整 ✅ | **主用**。接口稳定，有 `after` 分页，直接返回结构化 JSON |
| crt.sh | 无需认证 ⚠️ | 公共实例经常超时、无 SLA，JSON 接口时有时无 | 备用 |
| 自建 CT 日志消费 | 不需要 | 需要持续运行的消费端和几百 GB 存储 | 个人项目不现实 |

Cert Spotter 查询示例：

```
GET https://api.certspotter.com/v1/issuances
    ?domain=example.com
    &include_subdomains=true
    &expand=dns_names&expand=issuer
Authorization: Bearer <key>
```

返回每次签发的 `dns_names` 和证书 ID，用 `after=<last_id>` 翻页。本地按主机名去重，和已监控目标对比，差集就是"未纳管资产"。

### 4.2 归属验证

添加根域名时生成一次性 token，要求用户添加 TXT 记录：

```
_certsentry-verify.example.com.  IN TXT  "certsentry-verify=<token>"
```

用 `dnspython` 查询权威服务器确认后才开启发现。token 不过期但可轮换，防止验证通过后域名易主。

### 4.3 已知限制

- CT 日志只覆盖公开 CA 签发的证书，自签名和私有 CA 的证书发现不了。
- 通配符证书（`*.example.com`）不会暴露具体子域名。
- 日志入库有延迟，新证书可能几分钟到几小时后才查得到。

## 5. 通知渠道

全部走 HTTP Webhook，不需要企业资质。

| 渠道 | 接入方式 | 注意点 |
|---|---|---|
| 邮件 | `django-post_office` 或直接 SMTP；事务邮件用 Celery 异步发送 | 自建邮容易进垃圾箱。SaaS 用第三方（如 Resend，有免费额度）⚠️，并配置 SPF、DKIM、DMARC |
| 企业微信群机器人 | `POST https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=`，JSON `msgtype=markdown` ⚠️ | 每个机器人每分钟 20 条，需在发送端合并 |
| 钉钉群机器人 | 同上形式，必须实现 **加签**：`timestamp + "\n" + secret` 做 HMAC-SHA256，再 Base64 ⚠️ | 官方文档有现成示例，照做即可 |
| 飞书群机器人 | `POST` 到 hook 地址，带 `timestamp` 与 `sign`（把 `timestamp + "\n" + secret` 当 HMAC 的 key）⚠️ | 时间戳与服务器时差超过 1 小时会被拒绝 |
| 通用 Webhook | 用户自定义 URL，POST JSON，带 `X-Certsentry-Signature`（HMAC-SHA256） | 文档给出验签示例，方便用户接入自己的系统 |

消息模板统一用纯文本生成，再按渠道渲染。模板里包含：域名、剩余天数、到期日、颁发者、证书指纹前 8 位、控制台链接。

## 6. 数据模型补充

在需求报告第 7 节的基础上，补充约束和索引：

- `Target`：唯一约束 `(organization_id, hostname, port)`；索引 `(state, next_check_at)` 供派发器扫描，只建部分索引 `WHERE NOT is_paused`。
- `Certificate`：`sha256` 全局唯一。证书内容跨租户相同，共享存储能大幅减少行数，但查询时必须通过 `CheckResult` 关联，不能直接按组织查证书表。
- `CheckResult`：按月分区（PostgreSQL 声明式分区），90 天前的分区归档或删除。索引 `(target_id, checked_at DESC)`。
- `AlertEvent`：唯一约束 `(target_id, kind, threshold, cert_sha256)`，这是去重的核心。
- `Channel.config`：用 `django-encrypted-fields` 或自己用 Fernet 加密（密钥来自环境变量），数据库泄露也不会暴露机器人密钥。
- 所有业务表带 `organization_id`，并写一个自定义 Manager 强制过滤。**租户隔离要有测试**：用 A 组织的用户请求 B 组织的目标，必须 404。

## 7. 安全设计

| 威胁 | 对策 |
|---|---|
| SSRF | 解析后校验 IP：拒绝回环、私网（10/8、172.16/12、192.168/16）、链路本地（169.254/16，含云厂商元数据地址）、组播、IPv6 等价地址段；检测 worker 运行在不能访问内网的机器或容器网络 |
| DNS rebinding | 校验和连接使用同一次解析的结果，把目标 IP 固定传给连接函数，不让操作系统重新解析 |
| 凭证泄露 | Webhook 密钥加密存储，界面只回显掩码；API Token 只存哈希，只在创建时显示一次 |
| 滥用 | 注册邮箱验证、每组织额度、检测冷却、异常流量封禁（Admin 一键） |
| 注入与 XSS | ORM 参数化；模板默认转义；徽章 SVG 里的域名做白名单过滤 |
| 传输 | 全站 HTTPS（Let's Encrypt + Caddy 自动续期）；Cookie 设 `Secure`、`HttpOnly`、`SameSite=Lax` |
| 依赖漏洞 | `pip-audit` 接入 CI；Dependabot 或 Renovate 自动提 PR |

## 8. 部署架构

```
                ┌────────── Caddy（自动 HTTPS、反代、静态文件）
                │
   浏览器 ──────┤── Django（gunicorn，2 worker）── PostgreSQL 17
                │         │
                │         └── Redis 7
                │               │
                └── 不暴露 ─────┼── celery worker（gevent，检测）
                                └── celery beat（单实例）
```

- 一台 2 核 2 GB 的香港或新加坡 VPS 足够支撑演示站（几千个监控目标）。预算大约每月 30~60 元人民币。⚠️
- Caddy 而不是 Nginx：自动申请和续期证书，少一个要自己维护的组件。
- `docker-compose.yml` 同时服务两种场景：开发（源码挂载、热重载）和自部署（直接拉镜像）。
- 数据库每日 `pg_dump` 到对象存储或另一台机器，保留 7 天。
- 日志用 Docker json-file 驱动加轮转；错误进 Sentry（免费额度够用）。⚠️

## 10. 被否决的方案

| 方案 | 否决原因 |
|---|---|
| 用 `ssl.get_server_certificate` 做检测 | 拿不到证书链，无法判断链是否完整 |
| Scrapy 抓 crt.sh 网页 | 脆弱且违反对方预期用途；有官方 JSON API 就用 API |
| 自建 CT 日志消费端 | 存储和运维成本远超个人项目收益 |
| Celery + RabbitMQ | Redis 一个组件同时做 broker 和缓存，少维护一个服务；本项目消息量不需要 RabbitMQ 的投递保证 |
| Django Channels 做实时推送 | 检测结果用 HTMX 轮询即可，引入 ASGI 和 channel layer 不值得 |
| 前端用 React | 见 2.3 |
| Kubernetes 部署 | 单机 docker-compose 足够，简历上写 K8s 但没有真实规模会被看穿 |

## 11. 主要风险与验证计划

| 风险 | 如何在第 1 周验证 |
|---|---|
| gevent 与某些库不兼容（尤其是 `cryptography` 的阻塞调用） | 写 100 并发的最小脚本压测，确认无死锁；`cryptography` 是纯计算且很快，预计无问题 |
| Python 3.13 的 `getpeercertchain()` 行为 | 开工第一天写探测脚本确认返回内容；若不可用，改用 `ssl.MemoryBIO` 手动握手 |
| Cert Spotter 免费额度不够 | 注册账号实测；不够就对每个根域名每天只拉一次增量并缓存 |
| 邮件送达率 | 用自己的域名先发 20 封到主流邮箱，看是否进垃圾箱，再决定是否换第三方 |
| 目标站点封禁数据中心 IP | 记录出口 IP 并写进文档，检测失败时提示用户加白名单 |
